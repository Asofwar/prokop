# Нумерация релизов Prokop

Версия имеет вид `MAJOR.MINOR.PATCH`, например `2.1.0`. Других форм сборка не принимает (`build.yml` проверяет формат `x.y.z`).

## Какую цифру увеличивать

- **MAJOR** (`2.1.0` → `3.0.0`): обновление требует от пользователя действий или ломает совместимость. Например, переименование пакета или конфигурации, удаление опций без автоматической миграции, переход, после которого откат на прежнюю версию невозможен без ручных шагов.
- **MINOR** (`2.1.0` → `2.2.0`): новые возможности или большой набор исправлений, например законченный этап аудита. Обновление ставится поверх, настройки переносятся сами.
- **PATCH** (`2.1.0` → `2.1.1`): только срочные исправления, без новых возможностей и без новых миграций конфигурации. Безопасно ставится поверх.

При увеличении старшей цифры младшие обнуляются.

## Как выпускается релиз

1. Релиз собирается только из `main`.
2. В `RELEASE_VERSION` записана версия будущего релиза. Её поднимают в начале работы над ним, а не в момент выпуска.
3. Заметки лежат в `docs/releases/<версия>.md`: по-русски, для пользователя. Они описывают, что изменилось, что нужно сделать при обновлении (если что-то нужно) и что проверено (PASS / NOT TESTED, в том числе на роутере).
4. Перед выпуском CI на `main` должен быть зелёным.
5. Релиз выпускается запуском workflow «Build packages» на `main` с `release_tag` = версии из `RELEASE_VERSION` и `publish_release` = true. Workflow сам создаёт тег и релиз, а описание берёт из `docs/releases/<версия>.md`. Тег всегда совпадает с `RELEASE_VERSION`.
6. Опубликованная версия не пересобирается под тем же номером. Если что-то нужно поправить, выходит следующий PATCH.
